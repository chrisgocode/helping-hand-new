# AI failure normalization plan

## Decision

Use two small, separate translations:

```text
OpenRouter SDK failure
        ↓
TaskAi provider-neutral failure
        ↓
controller HTTP Problem Details response
```

`TaskAi` owns provider interpretation. Controllers own HTTP. Neither the task
module nor the web/mobile clients should know about OpenRouter error classes,
status codes, response bodies, or headers.

This gives the `TaskAi` module a deep interface: callers keep using the existing
three task-AI methods while timeout handling, provider classification, structured
output validation, and data redaction remain hidden in its implementation.

## Why this seam belongs in `TaskAi`

All model calls already pass through `TaskAi.#complete`. That is the narrowest
seam with the most leverage: normalize a provider failure once instead of adding
OpenRouter-aware branches to every controller or task operation. It also keeps
the implementation local to the only module that imports the OpenRouter SDK.

The controller is the correct adapter from an application failure to an HTTP
response. Putting HTTP status codes in `TaskAi` would couple an otherwise reusable
AI module to Hono and prevent non-HTTP callers from using the same interface.

Do not add a provider interface, factory, error subclass per status, circuit
breaker, or retry framework yet. There is one provider and one call path; those
abstractions would add surface area without current leverage.

## Internal failure contract

Add one `TaskAiError` with a closed `kind` union:

| Kind | Meaning | Retryable |
| --- | --- | ---: |
| `timeout` | The client or upstream exceeded its response deadline | Yes |
| `unavailable` | Connection failure, throttling, overload, or transient upstream failure | Yes |
| `invalid_response` | The provider returned missing, malformed, or semantically invalid structured output | Yes |
| `configuration` | Credentials, billing, model, permissions, or the request generated by this application are invalid | No |
| `unknown` | An unclassified implementation failure | No |

`retryable` should be derived from `kind`, not accepted independently by the
constructor. The error may retain the original exception as `cause` for local
debugging, but `cause` must never be serialized or passed to production logging.

An optional, sanitized `retryAfterSeconds` may be retained for a provider 429 or
503 when the SDK exposes a valid value. Accept only an integer in a conservative
range; do not forward arbitrary provider header values.

Retain an optional numeric `providerStatus` for internal logging and metrics. It
is safe operational context for distinguishing credentials, billing, and outage
failures, but it must not enter the public response.

Do not expose provider names, model names, upstream status codes, prompt content,
generated content, or raw response bodies through this contract.

## OpenRouter classification

The installed `@openrouter/sdk` version is `1.2.86`. It exposes client-side
`RequestTimeoutError` and `ConnectionError`, an `OpenRouterError` carrying an HTTP
status, and structured response/SDK validation errors. It also accepts
`timeoutMs` and retry configuration.

Classify at the `#complete` seam as follows:

| OpenRouter/SDK condition | `TaskAiError.kind` |
| --- | --- |
| `RequestTimeoutError`, HTTP 408, HTTP 524 | `timeout` |
| `ConnectionError`, HTTP 429, 500, 502, 503, or 529 | `unavailable` |
| Missing text, invalid JSON, Zod mismatch, wrong/duplicate/missing task IDs | `invalid_response` |
| HTTP 400, 401, 402, 403, 404, 413, or 422; SDK request validation | `configuration` |
| Anything else | `unknown` |

Use the stable client error classes for network failures and the SDK's base HTTP
error plus `statusCode` for provider responses. Avoid importing every generated
status-specific subclass; that would unnecessarily couple the implementation to
the SDK's generated class layout.

The ID-set invariants currently checked after `#complete` are also provider
response validation. They must throw `TaskAiError('invalid_response')`, rather
than escaping as generic `Error` instances.

Provider 429 deliberately becomes application HTTP 503. Returning 429 would make
an OpenRouter quota/overload indistinguishable from Helping Hand's own request
rate limit.

## HTTP error contract

Use RFC 9457 Problem Details with the `application/problem+json` media type. A
small formatter in `apps/api/src/lib/problem.ts` should be the single HTTP
adapter. Put the shared response schema in `packages/schemas/src/problem.ts`
because both web and mobile clients consume this public contract.

Use stable URNs now; they do not require owning a domain:

```json
{
  "type": "urn:helping-hand:problem:ai-timeout",
  "title": "AI generation timed out",
  "status": 504,
  "detail": "The AI service did not respond in time. Try again.",
  "instance": "urn:request:01J...",
  "retryable": true
}
```

The `type` is the machine-readable code, so a second `code` field would be
redundant. `retryable` is a useful Problem Details extension for clients. The
existing `X-Request-Id` should remain on the response and supply the opaque value
used by `instance`.

| Internal kind | HTTP | Public type | Public title | Retryable |
| --- | ---: | --- | --- | ---: |
| `timeout` | 504 | `urn:helping-hand:problem:ai-timeout` | AI generation timed out | Yes |
| `unavailable` | 503 | `urn:helping-hand:problem:ai-unavailable` | AI generation is temporarily unavailable | Yes |
| `invalid_response` | 502 | `urn:helping-hand:problem:ai-invalid-response` | AI generation returned an invalid response | Yes |
| `configuration` | 500 | `urn:helping-hand:problem:internal-error` | Internal server error | No |
| `unknown` | 500 | `urn:helping-hand:problem:internal-error` | Internal server error | No |

Set `Retry-After` only when a sanitized upstream hint exists. Do not invent one
for timeouts or malformed output. The UI can always use `retryable` to preserve
the draft and offer a manual **Try again** action.

RFC 9457 defines the standard Problem Details members and permits extension
members such as `retryable`. RFC 9110 defines 502 for an invalid upstream
response, 503 for temporary unavailability, and 504 for an upstream timeout,
which matches these meanings.

## Timeout and retry policy

Configure the OpenRouter client with a 30-second `timeoutMs`. Keep SDK retries
explicitly disabled initially.

OpenRouter already performs provider fallback by default, and this application
already requests providers that support the required structured parameters.
Adding another retry layer can duplicate spend and turn one 30-second failure
into a poor interactive experience. These proposal operations do not persist
changes, so the client can safely preserve its draft and let the user retry.

Revisit automatic retry only if production measurements show a meaningful class
of short transient failures that provider routing does not absorb. If added,
permit at most one bounded retry, honor `Retry-After`, use jitter, and keep the
whole operation within a single end-to-end deadline.

## Logging and metrics

Continue producing one completion log from the existing AI observability
middleware. Add only normalized, low-cardinality fields:

- `event`: `ai_request_completed`
- `operation`: `breakdown`, `durations`, or `order`
- `failureKind`: the internal normalized kind when unsuccessful
- `providerStatus`: a numeric upstream status when one exists
- `status`: the application HTTP status
- `model`: the configured model identifier
- `durationMs`
- `requestId` through the existing child logger

Use `warn` for `timeout`, `unavailable`, and `invalid_response`; use `error` for
`configuration` and `unknown`; keep successful calls at `info`.

Never log the provider exception, `cause`, response body, prompt, task title,
generated output, authorization headers, API key, user email, or IP address.
The request ID is the safe correlation handle. Aggregate counts and latency by
operation, status, and `failureKind` before considering a dedicated metrics
system.

To preserve one completion event, `handleTaskError` should put the normalized
failure kind and safe numeric provider status in request-local Hono context. The
existing `logAiRequest` middleware can then include them after `next()` returns;
it should not emit a second error event for the same failure.

## Test plan

### 1. `task-ai.test.ts`

Keep the unit tests colocated with `TaskAi` and make classification table-driven:

- client timeout and HTTP 408/524 become `timeout`
- connection failure and HTTP 429/500/502/503/529 become `unavailable`
- HTTP 400/401/402/403/404/413/422 become `configuration`
- missing content, invalid JSON, Zod failure, and semantic ID-set failures become
  `invalid_response`
- an unknown exception becomes `unknown`
- the client receives `timeoutMs: 30_000` and retries are disabled
- retryability is derived correctly

### 2. `task.routes.test.ts`

At the HTTP adapter seam, assert for every normalized kind:

- exact HTTP status
- `Content-Type: application/problem+json`
- stable `type`, `title`, `status`, `detail`, `instance`, and `retryable`
- preserved `X-Request-Id`
- sanitized `Retry-After` behavior
- OpenRouter error text, response bodies, prompts, and secrets never appear
- provider 429 maps to 503 while Helping Hand's own limiter remains 429

### 3. Observability test

Capture Pino output and verify that the event includes only normalized fields.
Use an intentionally sensitive provider message and task title, then assert
neither appears in the serialized log.

### 4. Opt-in live model test

Add a colocated `task-ai.live.test.ts` that is skipped unless
`RUN_LIVE_AI_TESTS=1`. Exercise one small request for each of the three operations
against the configured real model and validate only the public invariants. Keep
it out of pre-commit and normal CI because it is network-dependent and costs
money.

Suggested local invocation:

```sh
cd apps/api
RUN_LIVE_AI_TESTS=1 bun --env-file=.dev.vars test src/services/task-ai.live.test.ts
```

Timeouts, 429s, 5xx responses, and malformed payloads should remain deterministic
unit tests using the existing SDK mock. A real provider is not a reliable fault
injection tool.

## Implementation order

1. Add failing `TaskAi` classification and timeout tests.
2. Add `TaskAiError` and normalize all SDK, parsing, and semantic-output failures
   inside `TaskAi`.
3. Add the shared Problem Details schema and minimal Hono formatter.
4. Add failing route tests, then translate `TaskAiError` in `handleTaskError`.
5. Extend the existing Pino event with normalized failure fields and redaction
   tests.
6. Add the opt-in live tests and run them manually with the real OpenRouter key.

The API currently returns several ad hoc `{ "error": "..." }` shapes. The
Problem Details formatter should be reusable, but migrating every non-AI error is
a separate mechanical cleanup and should not block this reliability work.
