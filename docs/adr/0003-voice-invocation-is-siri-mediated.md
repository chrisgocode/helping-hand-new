# Voice invocation is Siri-mediated, not wake-word

A voice-first guided session needs a way to begin without touching a screen. We start sessions from an explicit invocation — a Siri App Intent, a control on the recipient's device, or a resumed session already in progress — and run our own wake word only inside an active session, if at all. We do not listen for a wake word while the app is idle. Continuous ambient listening fails on three independent grounds, each sufficient on its own: iOS will not sustain it, App Review will not accept it, and the glasses cannot power it. A design that requires all three to change is not a design we can build against.

## Considered options

- **A custom wake phrase detected continuously on device.** Rejected on three counts. iOS blocks starting capture from the background outright, and does not reliably sustain a session started in the foreground; developers report the process killed roughly 46 seconds after backgrounding despite an active audio engine, across many category and option combinations. App Review offers no background mode for continuous capture: the `audio` mode is scoped to playback, and Apple's stated rationale is that the user is reminded the session is live by ongoing sound, which a silent listener cannot satisfy. Guideline 2.5.14 separately requires consent and a clear indication while recording. Finally, holding HFP open continuously pins glasses output to 8 kHz for the entire time, monopolizes the shared Bluetooth audio route against calls and Meta AI, and exhausts a battery rated for about 5.5 hours of continuous call audio.
- **A background App Intent that starts a session without foregrounding the app.** Rejected: `authenticationPolicy = .alwaysAllowed` permits a background intent to run on a locked device, but a background intent cannot start audio capture. The capture restriction and the lock restriction cannot both be satisfied by the same intent.
- **Waiting for Meta to ship third-party voice invocation.** Rejected as a dependency, accepted as a future path. Meta documents no third-party wake-word or voice-invocation capability, and toolkit sessions are app-initiated. We build behind an interface that can adopt it later rather than blocking on an unannounced capability.
- **Relying on the phone's lock screen alone.** Rejected: it is the fallback, not the design. A recipient with hands occupied cannot be required to find and unlock a phone to hear the next step.

## Consequences

- **Siri invocation costs one unlock.** An App Intent with `openAppWhenRun` brings the app to the foreground, and foreground launch requires an unlocked device; Apple treats this as correct behavior, not a policy we can opt out of. In practice "Hey Siri, start my morning routine" is followed by a Face ID glance rather than a tap, which is acceptable for most recipients and blocking for some.
- **The primary path assumes a dedicated recipient device.** A recipient already signs in once through enrollment and holds an effectively non-expiring session, so the app in the foreground with the idle timer disabled for the duration of a guided session is a reasonable resting state. That path has no lock-screen problem at all, and Siri becomes the convenience entry rather than the load-bearing one.
- **Invocation is pluggable; the task engine is not.** Entry points — Siri, an on-device control, a session already running — converge on the same session start. The engine does not know which one fired, so adding an entry point later, including a native Meta invocation, changes nothing below the voice interface.
- **Wake-word licensing and integration are deferred.** In-session wake words are the last thing built, and only if sessions show a need for them. Their value is gated on command accuracy against recorded 8 kHz beamformed glasses audio, which is the test that decides whether voice control is viable at all.
- **Route interruption is the real reliability surface.** With ambient listening gone, the remaining failure mode is a session losing its microphone route mid-task — an incoming call, Meta AI invoked on the glasses, a Bluetooth reconnect. Sessions must observe audio interruption and route-change notifications and recover the route, because a guided session outlives any single audio interruption.
- **Idle behavior is defined by silence, not by listening.** After a period without input a session returns to its resting state and releases HFP, restoring high-quality output. Resuming requires invocation again, which is the cost of not listening continuously.

## Revisit when

Meta exposes third-party voice invocation, or Apple sanctions a background mode for assistant-style capture. Until then, re-proposals of ambient listening should be checked against all three blockers above; clearing one of them is not enough.
